# Real location and map checks — both KAYAN demos

## What changed

Both apps use the Capacitor 7 Geolocation plugin on Android (browser geolocation in web previews). The passenger map uses Leaflet/OpenStreetMap; the driver map uses Google Maps. Driver location starts automatically when the map opens; passenger location remains opt-in. Android requests foreground coarse and fine location together; the operating system may grant approximate access or deny the request. High accuracy is requested with no accepted cached age; Android uses a 15-second location request interval and 5-second minimum update interval, while browser geolocation allows up to 60 seconds for the initial fix. These settings are requests, not accuracy guarantees or guaranteed timing.

A device marker shows reported coordinates. Older than 30 seconds, paused, waiting, or failed fixes are not labelled current; their marker is grey. Android uses its available location sources, potentially GPS, Wi-Fi, mobile networks or emulator mock location. The app cannot certify satellite-only or non-mocked readings.

Leaving the map screen, app backgrounding and component cleanup clear the location watch. Returning to the foreground resumes enabled tracking, checking permission again. Tracking is not persisted between launches. There is no background-location permission or foreground tracking service. No camera, microphone, contacts, telephone, file or notification permission is requested because those interactions remain demos.

Native Android manifests and eagle icons are generated by `src/android/prepare-android.mjs` in both APK workflows after Capacitor sync. The script adds coarse/fine foreground permissions, optional GPS hardware, five launcher densities and adaptive icons. Each app keeps its separate package ID. Capacitor's default internet permission supports map loading. Existing eagle artwork is kept intact on a forest-green background.

## Map service and privacy

The passenger map uses `https://tile.openstreetmap.org/{z}/{x}/{y}.png`, with visible attribution. The driver uses the native Google Maps Android SDK in APKs and Google Maps JavaScript API in browser previews; Google Routes API calculates driving routes in both. Native map display requires the Android-app-restricted `VITE_GOOGLE_MAPS_ANDROID_API_KEY` (Maps SDK for Android only). Browser maps and route calculation require the website-restricted `VITE_GOOGLE_MAPS_API_KEY` (Maps JavaScript API and Routes API). Both keys need billing, internet access and appropriate package/signing-certificate or website-origin restrictions. Once a driver accepts a demo ride, the app requests alternate routes from the current device location to the destination, then displays the route with the shortest traffic-aware travel time. If current location is unavailable, no route is fabricated. Map providers receive the IP address and viewed area, and Google receives route origin/destination. No location is saved or sent to KAYAN. Google Maps billing and usage terms apply to the driver app.

Pickup and destination text, demo rides, stages, estimates and fares remain simulated. Actual device coordinates do not become a booking pickup, route, live driver or real ETA. There is no turn-by-turn navigation, dispatch, payment, upload or approval. Subscription prices and rewards remain unfinalized.

The new native permissions/plugins/icons require new APKs; refreshing the old APK cannot add them. Clean CI debug signing can differ between runs; if Android reports incompatible signatures, uninstall the old test app before installing the new trusted APK. This clears that app's local preferences. Do not bypass Play Protect.

## Required acceptance checks

Check the driver layout against Android window-size classes: compact width below 600dp uses the full phone width and bottom navigation. In the browser preview, all sections use a centered 430px phone frame with the same viewport height and bottom navigation above 600px; Earnings and Trip History content scrolls inside the frame, earnings summary cards and balance panels stack vertically, and trip-history rows remain readable. On an Android tablet, medium (600–<840dp), expanded (840–<1200dp), large (1200–<1600dp), and extra-large (1600dp and above) use progressively wider non-trip layouts with top navigation. During a trip or while online, keep the map edge-to-edge on the actual device. Verify short (<480dp), medium (480–<900dp), and expanded (900dp and above) heights keep the map controls and request panel usable without forcing the app wider than the viewport.

1. **Logo:** Install both APKs together. Confirm both show the KAYAN eagle (including round/adaptive launcher masks), different app names, and separate package IDs. Confirm eagle branding appears on mobile headers and browser favicon.
2. **Permission timing:** On the driver app, opening the map automatically requests location. Choose While using the app and grant the requested permission. Confirm a marker and coordinates appear. The passenger app should still wait for its explicit location opt-in. No other runtime permissions should be requested.
3. **Approximate/denied:** Test Approximate-only and denial. The OS controls the granted permission; denial must not invent a position or stop demo bookings. For permanent denial, grant permission through Android App settings and retry location in the driver app.
4. **Services off:** Disable Android Location; retry. Confirm an actionable error and no current-position claim. Turn Location and Google Location Accuracy on; retry.
5. **MuMu:** Configure MuMu's simulated location using the emulator's location controls, choose a known coordinate, enable Android Location and ensure Google Play Services is present. Compare app coordinates with that configured point; change the simulated point and confirm updates. Emulator success validates the integration, NOT physical GPS accuracy.
6. **Physical device:** Test outdoors with clear sky on a real Android phone. Compare with Google Maps/device location at a known point and record horizontal accuracy and fix age. Walk a short route and confirm the marker changes; test indoors too. No numeric accuracy promise is valid without recorded results across devices/environments.
7. **Freshness:** Prevent further location fixes and wait over 30 seconds. Any retained fix must be labelled stale/not current and grey. Never interpret a stale or low-accuracy fix as reliable navigation.
8. **Lifecycle:** Open the driver map, background/lock the app, then return. Confirm tracking pauses and resumes. Navigate away from the map; Android's location-use indicator should stop (allow OS reporting delay). Check for duplicate watches or updates after leaving.
9. **Map and route:** On phones, confirm the Drive/Earnings/Trip history navigation stays available in a fixed bottom bar while the page scrolls vertically without horizontal overflow; on larger screens, confirm the navigation remains across the top. On the idle Drive dashboard, the journey heading and online switch appear between the section bar and map; when online, a reduced-motion-aware pulse highlights the switch and an elapsed `HH:MM:SS` timer advances until the driver goes offline. While online on Drive, the map should fill the screen below the app header and above the bottom navigation, including after declining a request. The bottom request/status panel should group the online timer with simulated earnings, completed trips and vehicle, and show pickup, destination, illustrative fare and request actions when a request is pending. Active trips retain compact stage, chat/call, advance and cancel controls. Switching to Earnings or Trip history leaves the map view; switching back to Drive restores it. Complete or cancel the trip to return to the dashboard. In the browser preview, one-finger vertical swipes over the map should scroll the page; use two fingers to pan/zoom the map. Confirm the Android APK shows the native SDK map, not a JavaScript-rendered map, and that the browser preview keeps its interactive JavaScript map. Accept a demo trip and confirm its route appears. Route errors should identify API key, restriction, billing or network setup rather than creating an invented line.
10. **Pre-registration and phone login:** Confirm entering a phone number requires WhatsApp consent, sends an OTP, and advances progress to a distinct code-verification step; Back returns to the phone field. An invalid code must not advance, while a valid code does. Test `097...` and `+260...` formats. Sign out and verify WhatsApp OTP returns to the same saved profile; test an existing anonymous profile is linked without changing its ID. Then upload the required driving licence, national registration card, vehicle registration, and roadworthiness certificate (PDF/JPG/PNG, each <=10 MiB). Use non-sensitive test files only; documents land in private Supabase Storage.
11. **Regression:** Accept/decline, complete/cancel, chat/call demos, earnings/history, pre-registration and Light/Dark/System must remain simulations. Confirm the Google map switches between the default light map and KAYAN dark map in Light, Dark and System appearance modes, including after going online. Driver Online does not automatically request GPS or enable dispatch.
